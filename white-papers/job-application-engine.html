Buying back time

Finding jobs, tailoring résumés, and filling forms takes time. I built two managers to handle that overhead.

OpenClaw gives both managers context about my experience and preferences. Each manages a separate job list, with a daily target of ten relevant roles.

While they find jobs, prepare résumés, and fill applications, I can study, read, or run. I choose the jobs and review the applications before they are sent.

From job discovery to my review

Each manager selects skills from my request and its saved progress. The order is fixed: approve the jobs, prepare all résumés, then fill applications one at a time.

Make the shortlist realistic

Shortlists include a fit judgment, a reach label, and the specific experience gap. Realistic matches come first; plausible stretch jobs appear separately. Senior technical roles requiring unsupported engineering, ML, or architecture depth stay out of recommended batches.

Recruitment roles are excluded. The managers also screen companies I have already applied to. YC sourcing stays off unless I send a specific job. These filters run before spending time on résumé preparation.

Where code saves model work

The model handles job fit, résumé tailoring, and personal answers. Reusable code handles known fields and saved progress.

One engine, two configurations

Both managers use one engine. Small adapters supply separate identities, queues, and windows, so a code improvement reaches both.

manager = {
    "id": "job-search",

Several fields, one model call

One executor call handles up to 12 field writes by default: read, match, fill, and check. Intermediate browser observations stay inside the call; the model receives the result.

// Simplified execution loop
for (const field of knownEmptyFields) {
  const answer = verifiedAnswerFor(field);
  if (!answer) continue;
  await fill(field, answer);
  if (!await valueMatches(field, answer)) break;
}

The executor preserves existing answers and keeps custom wording tied to its job. It currently handles Ashby text fields; other controls use model-guided browser actions.

Read less, resume precisely

Managers read only the relevant skill and current checkpoint. Reusing reviewed résumés and saved answers avoids repeated reading and writing.

python3 checkpoint_view.py checkpoint.json   --pointer /jobs/0 --field /status

Coordinate the browser, then let go

Only one manager owns native browser focus at a time. It keeps that turn through its approved batch, then releases control for the next authorized manager. Repeated start requests should resume saved work rather than create another controller.

Cleanup preserves application tabs and entered answers. The saved runs record ownership release and JavaScript resets; full native-session disposal remains unverified. Background work reduces supervision, though native interaction can still require browser focus.

Stay connected away from my desk

I follow progress over Telegram and send jobs I find on X or while browsing. Saved links enter the same approval workflow. The managers use my résumé, preferences, and email context to prepare personalized replies, with JM1 coordinating drafts for my review.
